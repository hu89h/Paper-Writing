# 质量检查要点

按判断需要使用，不要求逐项填写报告。结论进入对应资源说明，过程留在 Git 中；只做静态阅读。

## 内容与依据

- 是否有可定位的规则、步骤、示例或实现，而不只是能力宣传？
- 规则是否自洽；作者偏好、特定学科或会议习惯是否被写成普适标准？
- 输出格式、schema 和正文判定是否一致？
- 是否区分缺少证据、已证实错误和不适用，避免把未检查写成通过？

## 实现与依赖

- 关键能力的实际输入、处理与输出是否支持宣称？直接依赖是否改变这一判断？
- 结构检查、来源重算、数值匹配和语义归属分别能证明什么？
- 是否存在能推翻关键推断的静态反例？将其写成推断，不写成已运行测试。
- 依赖、环境及覆盖范围有哪些已知限制？不要由脚本或测试存在推断运行正确。

## 补充价值

- 与已入库的哪些具体内容重合，是否补充更清楚的步骤、示例或实现？
- 是否共同来源或改编，不能视为独立证据？
- 是否有清楚且值得维护的保留范围，还是需要修订核心前提才有价值？
- 材料不足时明确暂缓或未审，不为给整仓结论而无限扩展阅读。
