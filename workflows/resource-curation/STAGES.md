# 仓库审查参考细项

供复杂审查按需参考。输入是已经提供的仓库；只做静态阅读，不执行候选资源。简单任务直接按 [主流程](WORKFLOW.md) 处理即可。

## 1. 接收已有仓库

- 确认名称、来源和可阅读位置，查看 [资源目录](../../resources/CATALOG.md) 和 [变更记录](../../resources/CHANGELOG.md)。
- 核对已有登记及历史删除、排除原因；留意改名、镜像、同名和派生关系。
- 已有材料直接复用；缺少关键内容时说明缺口，不把审查扩展成候选发现任务。

完成后应能说明处理的是哪个仓库、依据哪些材料、这次审查的范围是什么。

## 2. 检查自身质量

- 先读 README 和目录，定位核心规则、参考资料、模板及脚本，再选择关键内容深入阅读。
- 检查内容是否实质，关键规则是否自洽，假设与学科范围是否清楚，宣称的能力是否有对应实现或材料。
- 区分“要求 Agent 做某事”和“提供实现该功能的脚本”。脚本存在不等于运行正确。
- 对重要描述区分源码事实、作者自述、分析推断和未知，保留可定位的原文依据。
- 明确未读范围，不把“本次未发现”写成确定不存在。
- 能力依赖脚本时核对关键输入到输出的逻辑，追读影响结论的直接依赖；静态反例是推理依据，不写成已运行测试。足以作出限定范围决定后无需扩展成全仓代码审计。

完成后应能指出具体优点、缺陷和判断限制，不只复述项目宣传。

## 3. 比较现有重合与增量

- 以具体能力为比较对象，不把完整框架和一个局部模块直接排总榜。
- 只以已入库目录中通过的范围作为已有覆盖；待审候选不作为现成替代。
- 已入库资源为空时记为不适用并说明理由；不据此推断候选独特或自动通过。
- 查看已入库相关资源的实际内容，记录共同覆盖和独特内容。
- 需要判断重复或替代时，对照双方关键原文；文件名相同或定位相似只作为线索。
- 同一仓库可以只有部分内容值得保留。注明这些内容的位置、作用和增量。
- 没有足够的同类依据时保留不确定性，不宣称它优于其他资源。
- 比较步骤、示例、接口与实现粒度，不将目的重合等同于没有价值；记录共同来源，不当作独立支持。
- 批量审查注明决定时的基准，仅已完成登记的对象进入后续已入库比较。

完成后应能说明哪些值得保留、是否已有替代，以及这些判断由什么支持。

## 4. 决定处理结果

- 在保留、部分保留、暂缓和不保留中作出有依据的判断。
- 保留时说明具体价值和适用边界；部分保留时列明内容范围。
- 将保留内容定位到文件、小节或函数，并区分规范、示例、接口与实现设计；“供参考”不豁免核心质量问题。
- 信息不足时暂缓，注明关键未知项。
- 不保留时说明质量问题、重复程度、替代对象或范围不适合等具体原因。
- Star、内容数量和项目新旧不单独构成决定依据。

结论不超出静态审查能支持的范围，不写实际写作效果或运行验证结论。

## 5. 登记与记录

- 通过检查的内容直接写入 `resources/CATALOG.md` 与 `resources/MODULES.md`，说明作用、适用范围和具体入口；部分保留时列清未通过的范围。
- 接收清单与入库目录分开维护；`build_catalog.py` 只生成已接收材料导航，不覆盖入库记录。
- 在 [变更记录](../../resources/CHANGELOG.md) 追加实际处理结果及理由。
- 不保留的资源记录排除原因，避免重复引入；后续删除、修改和恢复同样追加记录。
- 恢复之前核对旧原因和新依据，不覆盖旧记录。
- 缩减、删除时检查同库剩余保留项及跨资源依赖；旧分析保留历史身份，不冒充当前能力。

详细的资源卡、对比表和决策文档按需使用，不要求每次创建全部文件。

## 6. 检查与提交

- 回到原文核对影响处理结论的关键依据，检查是否遗漏独特内容或混淆事实与推断。
- 检查相关条目、入口和链接是否同步，删改原因是否清楚。
- 人工核对目录、模块、审查和最新变更结论；接收清单检查脚本不验证入库语义。
- 处理不一致项后，将本次相关修改及记录形成一个本地 Git commit，不混入无关改动。
- 只完成部分流程时，说明实际结果和未完成项，不把后续阶段记为完成。
